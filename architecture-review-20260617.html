1. types.ts — 拆出存储适配器

Worth exploring

Files: src/types.ts → src/types.ts + src/storage.ts

Problem

types.ts 同时承担两个职责：定义数据结构 和 实现 localStorage 读写。 导入类型的地方被迫引入 loadNotebooks/saveNotebooks/generateId。 删除测试：如果砍掉 types.ts 的存储函数，复杂不会消失，但会集中到一个专门的存储模块 —— 这是信号。

Why it matters now

Supabase 同步已在路线图上。接入时你需要第二个存储适配器。当前只有一个适配器（localStorage）， seam 是假设性的；但第二个适配器一到，seam 就是真实的。现在拆出接口，Supabase 接入成本会大幅降低。

Before / After

BEFORE — 类型与实现在同一文件

types.ts
┃ Node / Connection / Notebook (types)
┃ NOTEBOOKS_KEY
┃ generateId()
┃ loadNotebooks() → localStorage
┃ saveNotebooks() → localStorage

AFTER — 接口与实现分离

types.ts — 纯类型 + ID 生成
┃ Node / Connection / Notebook
┃ generateId()
storage.ts — 存储接口 + localStorage 适配器
┃ interface NotebookStorage
┃ class LocalStorageAdapter
┃ NOTEBOOKS_KEY (private)

Benefits: 类型文件变纯，不再有副作用依赖。存储模块有清晰的接口，Supabase 适配器只需实现相同接口。 测试时可以直接传入 mock adapter。Locality: 所有存储逻辑（包括未来的网络请求）都在一个地方。

2. EditNodeModal — 不受控组件有潜在 Bug

Strong

Files: src/components/Modals.tsx:12-48

Problem

Modal 使用 const editingNode = { ...node } 做浅拷贝，然后通过 editingNode.name = e.target.value 直接修改对象属性。 没有调用 useState，所以 React 不会重渲染 —— 输入框之所以"能用"，是因为 浏览器的原生 <input> 自己维护了 DOM 状态。一旦 React 因其他原因重渲染（比如 undo/redo 在后台触发），用户正在编辑的内容会丢失。

Interface friction

这个模块的接口欺骗了调用者：看起来像是正常 React 受控组件，实际上有一个隐藏不变量 —— "调用期间不能发生父组件重新渲染"。这是浅模块的典型症状：接口几乎和实现一样复杂 （你需要知道它用 ref 来理解行为），但 leverage 几乎没有。

Before / After

BEFORE — 可变局部变量, 不受控

const editingNode = { ...node };
// ...
<input value={editingNode.name}
  onChange={e => editingNode.name = e.target.value} />
// React 不追踪这个变化!

AFTER — 受控 state + 初始值

const [name, setName] = useState(node.name);
const [content, setContent] = useState(node.content);
// ...
<input value={name}
  onChange={e => setName(e.target.value)} />
<button onClick={() => onSave({
  ...node, name, content
})} />

Benefits: 删除不确定行为，接口行为与调用者预期一致。 这个模块乍看很"浅"（一个小弹窗而已），但实际上隐藏了一个 bug，体现了浅模块的典型特征 —— 表面简单，细节有坑。 Locality: 所有模态状态都在 React 状态树里，不会因外部重渲染而丢失用户输入。

3. 坐标变换逻辑 — 抽出自包含模块

Worth exploring

Files: src/components/MindMap.tsx (lines 55-68, 180-192, 262-269) → src/lib/coordinates.ts

Problem

MindMap 中散落着 4 处坐标变换逻辑：
· screenPos() — 世界坐标 → 屏幕坐标
· nodeStyle() — 世界坐标 → CSS translate
· Drag onUp — CSS translate → 世界坐标（正则解析 + 逆变换）
· Search jump — 计算到达目标需要的 pan 值
这些纯函数被埋在 541 行的组件中，无法独立测试。删除测试：把这 4 个函数拿出来，它们不需要 React 就能验证正确性。

Coordinate math is pure

坐标变换不依赖 DOM、不依赖 React state、不依赖 context。 它是纯函数：(worldX, worldY, canvasW, canvasH, pan, scale) → {screenX, screenY}。 纯函数是最容易测试的代码 —— 但当前它藏在组件内部，测试成本等于端到端测试。

Before / After

BEFORE — 变换散落在组件各处

MindMap.tsx
├ screenPos (line 60)
├ nodeStyle (line 262)

AFTER — 独立模块 + 可测试

lib/coordinates.ts
├ worldToScreen(wx, wy, cw, ch, pan, scale)
├ screenToWorld(sx, sy, cw, ch, pan, scale)
├ panToCenter(targetWx, targetWy, cw, ch, scale)
└ tests: coordinates.test.ts ✓

Benefits: 3 个纯函数，约 40 行代码，独立于 React。Leverage: 调用方只需传数字，不用理解正则解析 transform 字符串的 trick。 Locality: 所有坐标逻辑集中在一个文件，未来加触屏支持或修改缩放行为只需改一处。

4. useUndo — 初始渲染产生重复快照

Speculative

Files: src/useUndo.ts

Problem

初始化时 undoStack 已包含一个初始快照。首次渲染后 useEffect 又 push 了一个内容相同的快照。用户第一次 Ctrl+Z 会"撤销"到完全相同的状态 —— 相当于需要 按两次撤销才能回到真正的上一步。对用户来说表现为"撤销第一次没反应"。

Fix

在 useEffect 中增加初始化守卫，跳过第一次推送。
或者改用 useRef(true) 作为 isInitial 标记，mount 后才开始记录快照。

Benefits: 修复用户感知的"撤销不灵敏"问题。影响范围小（3 行改动），优先级较低但修复成本极低。

🎯 首要建议

先修 Card 2（EditNodeModal 不受控组件）—— 这是唯一的 bug，而不是"改进建议"。 虽然触发条件比较隐蔽（需要在编辑模态打开时发生背景重渲染），但后果是用户数据丢失。 修复只需改 10 行代码，收益确定。

其次做 Card 1（拆出存储接口）—— 在 Supabase 集成之前先把 seam 准备好。 不要等到有了两个适配器才去抽象，那是事后补救。

Card 3（坐标模块） 会让代码更容易迭代，但不急 —— 可以在下次碰触屏支持或画布功能时顺手做。 Card 4 属于锦上添花，随时可以修。
